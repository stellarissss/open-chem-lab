## 四、偏差登记（本阶段核心产出）

### 4.1 【L2 · 须用户裁决】主求解引擎：发现显著更优的成熟方案

**实测事实**

| 维度 | chempy 0.10.2（规划主链） | phreeqpython 1.6.2（新发现） |
|---|---|---|
| 直接依赖数 | **46**（含 Sphinx、dot2tex、pycvodes、pykinsol、多套 ODE 后端） | **3**（numpy / scipy / periodictable） |
| 传递依赖 | 经 `pyodesys` 拖入 **Jupyter / notebook / nbconvert / jupyter-server** 整栈 | 无 |
| 容器安装 | `python:3.11-slim` 内 `pip install chempy` **>34 分钟未完成**（已终止） | 秒级 |
| 单次求解 | 稳态 11.5ms | **<1ms（实测 0.2–0.9ms）** |
| 对口能力 | 通用非线性平衡 + 动力学 | **USGS PHREEQC 引擎**：pH、物种分布、活度、离子强度、**饱和度指数 SI**、沉淀/溶解（`desaturate`）、**加料重算**、**溶液混合运算**（`s1*0.5+s2*0.5`） |
| 官方用例复现 | — | **9/9 PASS**（pH 8.123 / SI 0.384 / 混合 0.0005 / 加料 9.474） |
| 许可证 | BSD-2-Clause | **Apache-2.0**（与 LGPL-3.0 主链兼容） |
| 活跃度 | ★661，2026-10 | ★94，2026-09 |

**为何重要**：phreeqpython 的能力**几乎逐条对应**项目核心需求——「真实物质任意组合」对应溶液混合运算、「隐藏化学态/物种面板」对应 `species`、`solution_speciation` 对应元素/物种总量、「沉淀与溶解」对应 `si`/`desaturate`、`事件唤醒重算` 对应 `add()`。而 chempy 拖入的 Jupyter 栈与「单机自托管、全局总成本最低」直接冲突（CHARTER 第 2 条）。

**待决策**：是否将 phreeqpython 升为**电解质/水溶液平衡主引擎**，chempy 降为「动力学 ODE + AI 独立对拍」的辅助角色？此为 L2（改变技术栈基线、影响 ADR-0002/0006/0008 与 CHARTER 第 5 条组件链），须用户裁决。

### 4.2 【L2 · 须用户裁决】Reaktoro 的分发渠道与 LGPL 义务

**实测事实**：`reaktoro` 在 PyPI **404**（不在 pip 生态），仅 conda-forge 提供 2.13.0（1207 个构建文件）。规划（`design/05`、`ADR-0005`、CHARTER 第 5 条）把它列为「**动态链接 + 运行时可替换 + `lgpl-link-check` 校验**」的主链组件，并预设 pip/Docker 部署链——**两者不一致**，导致 M0 验证项 9 无法按原设计执行。

**用户裁决（2026-11-15，自定义方案 D，非主管给出的三选一）**：

> 将Reaktoro设计为独立微服务吧，与主进程实时通讯，使用gRPC或UDS等确保低延迟

主管评估：该方案把 conda-forge 专属渠道隔离在单个服务镜像内、主链保持 pip/Docker，**同时消解渠道冲突与 LGPL 动态链接义务的可落地性**，优于原建议 (B)；与 D6「单机自托管」不冲突（同一 Compose 内新增 `reaktoro-service`，进程间走本机 UDS / 回环）。仍须履行 LGPL-2.1 §6 义务，进程隔离不免除。原文与登记见台账 §9.1；因 D1 已升 phreeqpython 为主引擎，派生 **D2-补**（该微服务的职责定位），已于批次二由用户明确，见台账 §9.2。

### 4.3 【L1 · 建议裁决】资产转换命令错误，须换用

**实测事实**：规划（`design/04`、`tools/asset-pipeline/README.md`）写 `lualatex --output-format=dvi → dvisvgm --pdf --font-format=woff`，**两条路径均失败**：

| 路径 | 结果 | 根因 |
|---|---|---|
| DVI → dvisvgm | 退出码 254 / `PostScript error: undefined in pgfwOperand` | TikZ/PGF 在 DVI 模式注入 PostScript specials，dvisvgm 需 Ghostscript 解释 |
| `dvisvgm --pdf`（Ghostscript 10.02.1） | 退出码 252 / `The installed Ghostscript version 10.02.1 isn't supported` | dvisvgm 3.2.1 不支持该 GS 版本 |

**可行路径（实测通过）**：`lualatex → PDF → pdftocairo -svg`（poppler，成熟工具）。产物质量**优于规划预期**：纯 `<path>`、零 `<text>` / 零外部字体 / 零外部位图、21 个 `clipPath`、保留 `<g>` 分组、液位 `liquidLevel1=85` 与默认 50 的 SVG 内容确实不同（clip-1 路径 Y 从 367.84 → 338.15）。

**建议**：把转换链改为 `lualatex → PDF → pdftocairo -svg → svgo`，并同步 `design/04`、`tools/asset-pipeline`、`ADR-0004`。宏包源码仅存构建期临时目录，实测**未入库**（门禁通过）。

## 五、其他实测记录（支撑后续 ADR）

### 5.1 刚性 ODE 与 SP-1（ADR-0008 待验证项 1）

| 方法 | 一级动力学 A(10) 误差 | 刚性体系 nfev | 刚性体系耗时 |
|---|---|---|---|
| RK45 | 0 | 42500 | 259.3ms |
| **LSODA** | 0 | **262** | **1.48ms** |
| BDF | 0 | 548 | 21.2ms |
| Radau | 0 | 1194 | 30.7ms |

**结论**：SciPy `LSODA` 已内置「**Adams/BDF 自动刚性检测与切换**」（ODEPACK Fortran），无需硬编码时间阈值，且比 BDF 快约 14 倍——**正好兑现台账 4.3 / ADR-0008「不自适应硬编码阈值」**。`scikits.odes` 虽活跃（2025-01）但需编译 SUNDIALS，`assimulo` 停在 2018。建议 M0 起以 SciPy LSODA/BDF 为刚性积分主力，CVODES 作为可选加速（M1 再评估），避免为「必须上 CVODES」付出编译与维护成本。此为 L1 建议，需裁决。

### 5.2 AI 独立对拍与黄金用例原型

三条用例（0.1M 乙酸、0.01M 乙酸、半中和缓冲）由**独立解析解**与 **ChemPy 数值平衡**两条互不依赖的路径对拍：

| 用例 | 独立基准 | ChemPy | Δ |
|---|---|---|---|
| 0.1M 乙酸 | 解析二次方程 2.88135 | 2.88135 | 1.3e-9 |
| 0.01M 乙酸 | 解析二次方程 3.38756 | 3.38756 | 1.3e-8 |
| 半中和缓冲 | Henderson-Hasselbalch `-log10(Ka)` = 4.75696 | 4.75727（完整平衡） | 3.0e-4 |

前两条用精确二次方程，误差 ≤1.3e-8；缓冲用例的 Δ=3.0e-4 来自 **HH 近似（[Ac⁻]=[HAc]）与完整平衡数值解的物理差异**，不是数值错误，仍远小于 `tol_pH=0.02`；三条 `sane=True`。产出的 `golden-cases/v1` 结构含 `expected_pH`、`independent.{analytic,chempy,sane}`、`tol_pH`、`source`、`confidence`、`ai_crosscheck`、`human_signoff: PENDING(user)`。

**发现两个内容验算坑**（均须进 CI 规则）：

- PHREEQC 在缺少 Ca 时 `si('Calcite')` 返回 **-999 哨兵值**（非数值错误），若直接进黄金用例会误判，须列为非法输入；
- ChemPy `root()` 的 `sane=False` 与 `success=True` 可以同时出现（见 §4.6），黄金用例须同时校验两者，不能只看收敛标志。

### 5.3 网关基准（开放项 2）

| 实现 | 10k 回环 | rps | 平均延迟 |
|---|---|---|---|
| Fastify 5.12.8 (Node 22) | 2202ms | 4542 | 0.220ms |
| axum 0.8.9 (Rust 1.93, release) | 595ms | 16806 | 0.060ms |

axum 约 **3.7 倍**吞吐。但两者都远超 M1 实际需求（求解本身 11.5ms 量级，网络层非瓶颈）；选型更应看**长期维护成本**：solver-worker 已是 Python、wasm-view 是 Rust、前端是 TS，引入 axum 会增加第二套编译工具链（本轮 axum 首次编译耗时约 5 分钟且依赖下载多次超时）。此为开放项 2，须用户裁决。
