## 四、偏差登记（本阶段核心产出）

### 4.1 【L2 · 须用户裁决】主求解引擎：发现显著更优的成熟方案

**实测事实**

| 维度 | chempy 0.10.2（规划主链） | phreeqpython 1.6.2（新发现） |
|---|---|---|
| 直接依赖数 | **46**（含 Sphinx、dot2tex、pycvodes、pykinsol、多套 ODE 后端） | **3**（numpy / scipy / periodictable） |
| 传递依赖 | 经 `pyodesys` 拖入 **Jupyter / notebook / nbconvert / jupyter-server** 整栈 | 无 |
| 容器安装 | `python:3.11-slim` 内 `pip install chempy` **>34 分钟未完成**（已终止） | 秒级 |
| 单次求解 | 稳态 11.5ms | **<1ms（实测 0.2–0.9ms）** |
| 对口能力 | 通用非线性平衡 + 动力学 | **USGS PHREEQC 引擎**：pH、物种分布、活度、离子强度、**饱和度指数 SI**、沉淀/溶解（`desaturate`）、**加料重算**、**溶液混合运算**（`s1*0.5+s2*0.5`） |
| 官方用例复现 | — | **9/9 PASS**（pH 8.123 / SI 0.384 / 混合 0.0005 / 加料 9.474） |
| 许可证 | BSD-2-Clause | **Apache-2.0**（与 LGPL-3.0 主链兼容） |
| 活跃度 | ★661，2026-10 | ★94，2026-09 |

**为何重要**：phreeqpython 的能力**几乎逐条对应**项目核心需求——「真实物质任意组合」对应溶液混合运算、「隐藏化学态/物种面板」对应 `species`、`solution_speciation` 对应元素/物种总量、「沉淀与溶解」对应 `si`/`desaturate`、`事件唤醒重算` 对应 `add()`。而 chempy 拖入的 Jupyter 栈与「单机自托管、全局总成本最低」直接冲突（CHARTER 第 2 条）。

**待决策**：是否将 phreeqpython 升为**电解质/水溶液平衡主引擎**，chempy 降为「动力学 ODE + AI 独立对拍」的辅助角色？此为 L2（改变技术栈基线、影响 ADR-0002/0006/0008 与 CHARTER 第 5 条组件链），须用户裁决。

### 4.2 【L2 · 须用户裁决】Reaktoro 的分发渠道与 LGPL 义务

**实测事实**：`reaktoro` 在 PyPI **404**（不在 pip 生态），仅 conda-forge 提供 2.13.0（1207 个构建文件）。规划（`design/05`、`ADR-0005`、CHARTER 第 5 条）把它列为「**动态链接 + 运行时可替换 + `lgpl-link-check` 校验**」的主链组件，并预设 pip/Docker 部署链——**两者不一致**，导致 M0 验证项 9 无法按原设计执行。

**用户裁决（2026-11-15，自定义方案 D，非主管给出的三选一）**：

> 将Reaktoro设计为独立微服务吧，与主进程实时通讯，使用gRPC或UDS等确保低延迟

主管评估：该方案把 conda-forge 专属渠道隔离在单个服务镜像内、主链保持 pip/Docker，**同时消解渠道冲突与 LGPL 动态链接义务的可落地性**，优于原建议 (B)；与 D6「单机自托管」不冲突（同一 Compose 内新增 `reaktoro-service`，进程间走本机 UDS / 回环）。仍须履行 LGPL-2.1 §6 义务，进程隔离不免除。原文与登记见台账 §9.1；因 D1 已升 phreeqpython 为主引擎，派生 **D2-补**（该微服务的职责定位），已于批次二由用户明确，见台账 §9.2。

### 4.3 【L1 · 建议裁决】资产转换命令错误，须换用

**实测事实**：规划（`design/04`、`tools/asset-pipeline/README.md`）写 `lualatex --output-format=dvi → dvisvgm --pdf --font-format=woff`，**两条路径均失败**：

| 路径 | 结果 | 根因 |
|---|---|---|
| DVI → dvisvgm | 退出码 254 / `PostScript error: undefined in pgfwOperand` | TikZ/PGF 在 DVI 模式注入 PostScript specials，dvisvgm 需 Ghostscript 解释 |
| `dvisvgm --pdf`（Ghostscript 10.02.1） | 退出码 252 / `The installed Ghostscript version 10.02.1 isn't supported` | dvisvgm 3.2.1 不支持该 GS 版本 |

**可行路径（实测通过）**：`lualatex → PDF → pdftocairo -svg`（poppler，成熟工具）。产物质量**优于规划预期**：纯 `<path>`、零 `<text>` / 零外部字体 / 零外部位图、21 个 `clipPath`、保留 `<g>` 分组、液位 `liquidLevel1=85` 与默认 50 的 SVG 内容确实不同（clip-1 路径 Y 从 367.84 → 338.15）。

**建议**：把转换链改为 `lualatex → PDF → pdftocairo -svg → svgo`，并同步 `design/04`、`tools/asset-pipeline`、`ADR-0004`。宏包源码仅存构建期临时目录，实测**未入库**（门禁通过）。

## 五、其他实测记录（支撑后续 ADR）

### 5.1 刚性 ODE 与 SP-1（ADR-0008 待验证项 1）

| 方法 | 一级动力学 A(10) 误差 | 刚性体系 nfev | 刚性体系耗时 |
|---|---|---|---|
| RK45 | 0 | 42500 | 259.3ms |
| **LSODA** | 0 | **262** | **1.48ms** |
| BDF | 0 | 548 | 21.2ms |
| Radau | 0 | 1194 | 30.7ms |

**结论**：SciPy `LSODA` 已内置「**Adams/BDF 自动刚性检测与切换**」（ODEPACK Fortran），无需硬编码时间阈值，且比 BDF 快约 14 倍——**正好兑现台账 4.3 / ADR-0008「不自适应硬编码阈值」**。`scikits.odes` 虽活跃（2025-01）但需编译 SUNDIALS，`assimulo` 停在 2018。建议 M0 起以 SciPy LSODA/BDF 为刚性积分主力，CVODES 作为可选加速（M1 再评估），避免为「必须上 CVODES」付出编译与维护成本。此为 L1 建议，需裁决。

### 5.2 AI 独立对拍与黄金用例原型

三条用例（0.1M 乙酸、0.01M 乙酸、半中和缓冲）由**独立解析解**与 **ChemPy 数值平衡**两条互不依赖的路径对拍：

| 用例 | 独立基准 | ChemPy | Δ |
|---|---|---|---|
| 0.1M 乙酸 | 解析二次方程 2.88135 | 2.88135 | 1.3e-9 |
| 0.01M 乙酸 | 解析二次方程 3.38756 | 3.38756 | 1.3e-8 |
| 半中和缓冲 | Henderson-Hasselbalch `-log10(Ka)` = 4.75696 | 4.75727（完整平衡） | 3.0e-4 |

前两条用精确二次方程，误差 ≤1.3e-8；缓冲用例的 Δ=3.0e-4 来自 **HH 近似（[Ac⁻]=[HAc]）与完整平衡数值解的物理差异**，不是数值错误，仍远小于 `tol_pH=0.02`；三条 `sane=True`。产出的 `golden-cases/v1` 结构含 `expected_pH`、`independent.{analytic,chempy,sane}`、`tol_pH`、`source`、`confidence`、`ai_crosscheck`、`human_signoff: PENDING(user)`。

**发现两个内容验算坑**（均须进 CI 规则）：

- PHREEQC 在缺少 Ca 时 `si('Calcite')` 返回 **-999 哨兵值**（非数值错误），若直接进黄金用例会误判，须列为非法输入；
- ChemPy `root()` 的 `sane=False` 与 `success=True` 可以同时出现（见 §4.6），黄金用例须同时校验两者，不能只看收敛标志。

### 5.5 【收尾补验 C1 / C2】WASM 现象本体 + 3Dmol.js 真实 WebGL

**方法纪律**：先按用户规范联网调研「一切可用成品与经验」，确认现成 WASM 粒子引擎经 GitHub API 检索均为 ≤54 星小品（`pcisph-wasm` MIT ★54、`behaviours-rs` MIT ★13 等），**无成熟单体成品**；成熟表现层是 PixiJS（MIT，上轮 500 粒子 p95 1.2ms）。故采用「PixiJS 渲染 + 极薄自研 WASM 数值内核」，自研范围落在 CHARTER 允许的四类内，不重复造轮子。

**C1 · WASM 工具链与帧预算（受限 → 通过）**

- 官方 `static.rust-lang.org` 下载卡 7 分钟 → 按用户「镜像优先」改 `RUSTUP_DIST_SERVER=https://rsproxy.cn`，**3 秒**装好 `wasm32-unknown-unknown`。
- `cargo build --target wasm32-unknown-unknown --release` 成功；产物 **4328 字节、零外部 import**（不经 wasm-bindgen，纯 C ABI + 静态线性缓冲），导出 `init/step/count/positions_ptr/checksum/memory`。
- Node 22 原生 `WebAssembly.instantiate` 实跑 180 帧/组：

| 粒子数 | p50 | p95 | p99 | max | 预算 16.7ms |
|---|---|---|---|---|---|
| 500 | 0.0044ms | 0.0052ms | 0.0116ms | 0.0226ms | ✅ |
| 1000 | 0.0045ms | 0.0053ms | 0.0066ms | 0.0146ms | ✅ |
| 2000 | 0.0088ms | 0.0098ms | 0.0142ms | 0.0154ms | ✅ |
| 4096 | 0.0179ms | **0.0199ms** | 0.0312ms | 0.0752ms | ✅（余量约 **840 倍**） |

- 同 seed=777 跑 60 帧两次 checksum **完全一致**（确定性，可复现）；JS 侧读回 WASM 线性内存首粒子坐标一致。
- 归档：`data/m0/wasm_kernel.wasm` / `wasm_kernel_lib.rs` / `wasm_kernel_Cargo.toml` / `wasm_kernel_harness.mjs` / `wasm_bench_result.json`，复跑见 `RERUN.md` §2。

**C2 · 3Dmol.js 真实 WebGL（受限 → 通过）**

- **根因定位**：纯 `--headless` 无 X display 时，Chrome 144 的 SwiftShader 走 Vulkan/XCB 后端，`xcb_connect() failed → EGL_NOT_INITIALIZED → Exiting GPU process`，因此 `getContext('webgl')` 返回 null、上一轮观察到的 `clearDepth=null`。
- **解法（复用现成系统工具，未造轮子）**：`xvfb-run -a` 提供真实 X display + `--enable-unsafe-swiftshader --use-gl=angle --use-angle=swiftshader`。实测拿到 **WebGL 2.0**，`clearDepth=function`，`readPixels=[51,102,204,255]`（`pixelNonBlack=true`）。
- **球棍渲染**：3Dmol.js 2.5.5 `createViewer` → WebGL renderer 实例化 → 载入乙醇 9 原子 XYZ → `stick+sphere` 样式 → 640×640 canvas 读回 **17048 个非白像素**（`hasGeometry=true`）。证明不只是「有 context」，而是真实几何输出。
- 归档：`data/m0/webgl_real.html` / `mol_render_real.html`，复跑见 `RERUN.md` §3（含「3dmol-min.js 不入库、从 npm 取」的纪律说明）。

### 5.6 【收尾补验 C3 / C4】Kenney F3 销项 + reaktoro LGPL §6 实证

**C3 · Kenney 包内 LICENSE（受限 → 销项，CC0 1.0）**

三级一手证据（研发规范要求一级来源，不采信聚合搜索结果页）：

1. **官网页面**：`kenney.nl/assets/particle-pack` 带浏览器 UA 返回 HTTP 200，`<td>License</td> → Creative Commons CC0`（链接 `creativecommons.org/publicdomain/zero/1.0/`），og:description「Download this package (80 assets) for free, **CC0 licensed!**」。
2. **包内 `LICENSE.txt` 原文**（公开第三方镜像 `Calinou/kenney-particle-pack` 转录）：「Particle Pack (1.1) by Kenney Vleugels」「**License (Creative Commons Zero, CC0)**」「You may use these assets in personal and commercial projects. Credit would be nice but is **not mandatory**.」
3. **CC0 1.0 官方法典**：`creativecommons.org/publicdomain/zero/1.0/legalcode.txt`（HTTP 200 / 7048 bytes）。

> **诚实注记**：官网签名下载端点 `/download-link/{id}` 返回 `403 forbidden`（需会话/人机校验），按多引擎技能规范「遇验证码/风控立即停止、不规避」，未硬刷；包内 LICENSE.txt 经公开第三方镜像取得，与官网标注一致。CC0 与 LGPL-3.0 主链无冲突，不触发 LGPL/AGPL 义务。**F3 销项，可入库**（仍按台账限定：仅取通用音效 / 粒子贴图，卡通器材不入库）。

**C4 · reaktoro 独立微服务 LGPL §6 可替换性（受阻 → 通过）**

- **渠道破局**：首次 `conda create` 卡在 solving（`repodata.json` 全通道 12s 超时），exit code 因管道 `| tail` 失真被误判为成功。改用 `api.anaconda.org/package/conda-forge/reaktoro` 直取单包 URL，下载 `reaktoro-2.13.0-py311h9c93177_3.conda`（6.5MB）+ `_0` 构建对照，`tar --zstd` 解压。
- **元数据**：`license=LGPL-2.1-only`；depends 含 `phreeqc4rkt / autodiff / optima / thermofun / yaml-cpp / numpy / python 3.11.*`（印证 D2-补 的复杂/多相能力来源）。
- **动态链接硬证据**：Python 扩展 `reaktoro4py.cpython-311-x86_64-linux-gnu.so`（6.4MB）的 `DT_NEEDED` 含 **`libReaktoro.so`** + RPATH `$ORIGIN/../../..`；扩展仅 3 个自定义符号，核心 **2239 个**导出符号在独立 `libReaktoro.so`（42MB）→ 未被静态编入。
- **可替换性硬证据**：`libReaktoro.so` 的 SONAME = `libReaktoro.so`（**无版本后缀**）；`_0` 与 `_3` 两构建 SHA256 不同但 SONAME 完全一致。把 `_0` 的 `.so` 覆盖到 `_3` layout 后，`ldd` 显示扩展经 RPATH **成功解析到替换后的 `libReaktoro.so`** → LGPL §6「运行时可替换」机制成立。
- **合规补注**：conda 单包 `info/` 仅含 `recipe-scripts-license.txt`，**不含 LGPL 全文**；故 `lgpl-link-check` 须自行随附 `LICENSE.LGPL-2.1` 全文（规划双文本义务的补强，见 §7 入口）。
- UDS/protobuf 为成熟成品（grpc 官方支持 `unix:` scheme），无需自研传输层；M1 骨架阶段落服务契约。复跑见 `RERUN.md` §4。
