# 03 · 开发流程（文档驱动 · 敏捷轻量）

> 本文件是开发流程基准：**文档驱动开发（DocDD）+ 敏捷**，面向「单人 + AI Agent」。
> 技术/产品真理源见 `01-Architecture.md`，进度见 `02-Roadmap.md`，当前任务规格见 `specs/`。

---

## 一、总基调（最高优先级）

> 个人开发者、开源非盈利、娱乐性质——**不套企业级严格标准**。流程为开发服务，任何规则若让开发变慢而无实质收益，就简化。

三条不可动摇的底线（不因「轻量」放松，见 `01-Architecture.md` 第七节）：

1. **事实零错**：化学事实层数值必须准确。
2. **不重复造轮子**：动手前先搜开源成品与官方文档。
3. **不绕过重大变更约定**：触及产品定义、技术栈、许可证基线、里程碑验收口径的变更，先说明动机与影响、同步相关文件（重大变更需用户拍板）。

**角色**：用户是决策者（只裁决）；AI 是项目主管（出题、归纳、实现、留痕）。涉及玩法设计须逐一向用户确认细节，不省略、不自构假设。

---

## 二、单一任务闭环（按规模伸缩）

**没有固定步数**，按任务大小选路径，可跳过不适用步骤但留痕说明。

### 2.1 大任务（新体系 / 新玩法 / 架构变更）——完整链路

1. **对齐**：读 `AGENTS.md` → `02-Roadmap.md` → `01-Architecture.md` 相关节 → `specs/` 对应规格。
2. **写规格**：在 `specs/` 写一份切片规格（小而明确，聚焦「做什么行为 + 边界 + 验收标准」，不堆实现细节）。
3. **变更检查**：触及重大变更 → 先与用户确认并同步真理源。
4. **实现**：复用优先，先搜开源成品与官方文档；编码遵循 `01-Architecture.md` 工程结构与依赖规则。
5. **验证**：够用的最小充分证据即可（见第四节）。
6. **回写**：更新 `02-Roadmap.md` 状态 + 在 `AGENTS.md` 更新当前焦点 + 留痕（见第三节）。

### 2.2 小改动（文案 / 单参数 / 明显 bug）——精简路径

读现场 → 改 → 验（能验证就验证）→ 在 `AGENTS.md` 的变更留痕处记一行。比例原则优先，别为一句话改动走全套流程。

---

## 三、留痕与交接（轻量，非防护）

文档以**给人/给 Agent 读**为目的：**S**elected 仅必要、**S**ynthetic 精简提炼、**S**tructured 结构化——噪音即上下文成本。

AI 可直接修订任何文档：发现有误、过时、难执行时灵活调整是被鼓励的；约束是**留痕可追溯、不绕过重大变更**，而非禁止修改。

| 载体 | 作用 | 写法 |
|---|---|---|
| `AGENTS.md` | AI 第一站 + 当前焦点 + 变更留痕 | 极简；每次收尾更新「当前焦点」一行 |
| `02-Roadmap.md` | 进度唯一来源（里程碑/切片状态/下一步） | 每完成切片更新状态列 |
| `specs/spec-XXX-主题.md` | 切片规格与验收标准 | 一份一切片，见下节 |

> 会话级细节（临时上下文）按需在 `AGENTS.md` 记一行即可，不新建历史文件——避免历史文档积累污染上下文。

---

## 四、验证（无强制门禁）

- **不在每个任务收尾强制跑全套 CI**。质量靠「数值零错红线 + 最小充分证据 + 用户随时可打断」保障。
- 完成后**如实记录**做了哪些验证、哪些没做及原因。
- **历史门禁是资产、保留不动**：`docs/归档/research/data/m0/verify_m0_s2.py`（41 断言）、`s2-auth/verify_auth_s2.py`（38 断言）是阶段二已证明不确定性消解的历史证据，不因本流程删除或停用。
- 产品级门禁（`golden-cases` / `license-scan` / `lgpl-link-check` / `schema-validate` 等，见 `01-Architecture.md` 第七节）在 M1 骨架搭建后逐步接入，按需触发而非每任务强制。

## 五、Spec 怎么写

每份 `specs/spec-XXX-主题.md` 用固定骨架（模仿 `spec-001-骨架搭建.md`）：

```markdown
# spec-XXX · 主题
## 目标        # 这段切片要达成什么（一句话）
## 范围        # 做哪些 / 不做哪些（明确边界）
## 验收标准    # 可客观判定的条件（能跑通、数值零错、有证据）
## 技术要点    # 引用的架构约束、复用组件、数据结构（指向 01 的现行节）
## 任务拆解    # 可选：复杂切片拆成有序子步骤
## 状态        # 待开始 / 进行中 / 已完成
```

Spec 聚焦「行为 + 边界 + 验收」，**不写实现细节、不堆历史裁决**；切片完成即把状态改为「已完成」并在 `02-Roadmap.md` 同步。

## 六、变更分级（重大变更的判定）

| 级别 | 定义 | 处理 |
|---|---|---|
| L0 | 文案纠错、过时口径更新、明显 bug、文档与实证冲突修正 | 直接改 + 留痕（鼓励） |
| L1 | 技术选型、架构调整、非重大变更的设计变更 | 说明动机与影响 → 同步 `01-Architecture.md` → 留痕 |
| L2 | 产品定义、技术栈基线、许可证基线、里程碑验收口径 | **先与用户确认 → 同步真理源 → 留痕** |

发现 L2 项及时提出、不攒到最后、不替用户裁决。
