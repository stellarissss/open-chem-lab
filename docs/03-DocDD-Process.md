# 03 · 开发流程（文档驱动 · 敏捷轻量）

> 本文件是开发流程基准：**文档驱动开发（DocDD）+ 敏捷**，面向「单人 + AI Agent」。
> 技术/产品真理源见 `01-Architecture.md`，当前在哪见 `02-Roadmap.md`，当前任务规格见 `specs/`。

---

## 一、总基调（最高优先级）

> 个人开发者、开源非盈利、娱乐性质——**不套企业级严格标准**。流程为开发服务，任何规则若让开发变慢而无实质收益，就简化。

三条不可动摇的底线（不因「轻量」放松，见 `01-Architecture.md` 第七节）：

1. **事实零错**：化学事实层数值必须准确。
2. **不重复造轮子**：动手前先搜开源成品与官方文档。
3. **不绕过重大变更约定**：触及产品定义、技术栈、许可证基线、里程碑验收口径的变更，先说明动机与影响、同步相关文件（重大变更需用户拍板）。

**角色与权限**：用户是决策者（只裁决）；AI 是项目主管（出题、归纳、实现）。涉及玩法设计须逐一向用户确认细节，不省略、不自构假设。

**文档只装「下一个 Agent 开工时需要知道的信息」，不装「上一个 Agent 做了什么」**：一切历史归 git log 与已完成 spec；任何文档不设日志——变更记录、done 报告、交接文件等一律不要。当前 spec 是唯一的工作文档。

---

## 二、单一任务闭环（按规模伸缩）

**没有固定步数**，按任务大小选路径，可跳过不适用步骤但在 spec 状态区说明。

### 2.1 大任务（新体系 / 新玩法 / 架构变更）——完整链路

1. **对齐**：读 `AGENTS.md` → `02-Roadmap.md` → `01-Architecture.md` 相关节 → 当前 spec。
2. **补全规格**：把 spec 粗稿就地补全为正式规格（聚焦「做什么行为 + 边界 + 验收标准」，不堆实现细节）；涉及玩法/数值的细节先逐一向用户确认。
3. **变更检查**：触及重大变更 → 先与用户确认并同步真理源。
4. **实现**：复用优先，先搜开源成品与官方文档；编码遵循 `01-Architecture.md` 工程结构与依赖规则；包/模块命名以 01 第六节为准，需要偏差先询问。
5. **验证**：够用的最小充分证据即可（见第四节）。
6. **回写 + 铺路**：只产出三样东西——缺一不可、多一样都不要（见 2.3）。

### 2.2 小改动（文案 / 单参数 / 明显 bug）——精简路径

读现场 → 改 → 验（能验证就验证）。git commit 即全部记录，不写任何文档日志。比例原则优先，别为一句话改动走全套流程。

### 2.3 链式闭环：回写即铺路（三样产出物）

每个切片完成时，回写**只**产出以下三样，缺一不可、多一样都不要：

1. **`AGENTS.md` 当前焦点**：一句话，指向下一个切片；旧焦点随本次完成删去并更新，不保留。
2. **`02-Roadmap.md` 切片状态**：勾选当前切片、列出下一个切片名。若需变更方向/路线，必须先调用询问工具向用户发起询问，裁决后才能修改。
3. **下一个切片的 spec 粗稿**：在 `specs/` 新建，只写大略的**目标 / 范围 / 验收标准 / 技术要点**，方向明确、细节留白；状态标「粗稿」。

> 边界：回写不产生任何其他文件或记录——没有留痕、没有 done 报告、没有交接文档，过程与历史由 git log 承载。粗稿只写**正向的目标与边界**，不写决策过程、不写猜测性内容、不预支未裁决的玩法细节。

下一轮开工时，读该粗稿 → 就地补全为正式规格 → 走 2.1 完整链路。

## 三、现场文档（正向快照，无日志）

每份文档都是**当前现实的快照**，只回答「现在是什么、接下来做什么」。主要文档（01/02/03/AGENTS）由用户裁决后改写，开发 Agent 不得擅自修改；发现文档与实证冲突时先询问用户。

| 载体 | 只回答什么 | 收尾动作 |
|---|---|---|
| `AGENTS.md` | AI 第一站 + 当前一句话焦点 | 回写产物 ①：删旧焦点、写新焦点 |
| `02-Roadmap.md` | 当前在哪（阶段/切片状态）+ 下一步 | 回写产物 ②：勾当前切片、列下一切片 |
| `specs/spec-XXX-主题.md` | 该切片的现行规格与验收 | 状态改「已完成」，并按 2.3 铺下一粗稿 |

> 文档不新增任何历史性内容；一切历史由 git log 承载。

---

## 四、验证（无强制门禁）

- **不在每个任务收尾强制跑全套 CI**。质量靠「数值零错红线 + 最小充分证据 + 用户随时可打断」保障。
- spec 只写规格，状态区仅标状态，不写验收记录、验证清单或过程叙事；验证与过程由测试产物和 git log 承载。
- 产品级门禁随切片逐步接入（`license-scan` 已在 CI），按需触发而非每任务强制。

---

## 五、Spec 怎么写

每份 `specs/spec-XXX-主题.md` 用固定骨架（模仿 `spec-001-骨架搭建.md`）：

```markdown
# spec-XXX · 主题
## 目标        # 这段切片要达成什么（一句话）
## 范围        # 做哪些 / 不做哪些（明确边界）
## 验收标准    # 可客观判定的条件（能跑通、数值零错、有证据）
## 技术要点    # 引用的架构约束、复用组件、数据结构（指向 01 的现行节）
## 任务拆解    # 可选：复杂切片拆成有序子步骤；粗稿阶段可留白
## 状态        # 粗稿 / 待开始 / 进行中 / 已完成
```

Spec 是**规格不是日志**：聚焦「行为 + 边界 + 验收」，不写实现细节、不记过程、不追加历史段落。

**两阶段就地演进**（见 2.3）：
- **粗稿**：上一切片回写时预写，含目标/范围/验收/技术要点的大略，细节留白、方向灵活；状态「粗稿」。
- **正式稿**：本切片开工时就地补全任务拆解与细节，状态依次「待开始 → 进行中 → 已完成」。

两阶段共用同一文件，补全时直接改写留白处、不追加旧内容，始终只有一份现行 spec。完成后按 2.3 回写三样产出物。

**已完成 spec 即冻结**：状态「已完成」的 spec 是历史载体，不再追加或改写内容（历史归 git log 与旧 spec）；确需纠错，先询问用户。

## 六、变更分级

| 级别 | 定义 | 处理 |
|---|---|---|
| L0 | 文案纠错、过时口径更新、明显 bug | **代码/内容/当前 spec**：直接改（git 记录一切）；**主要文档（01/02/03/AGENTS）**：先询问用户，裁决后改写 |
| L1 | 技术选型、架构调整、非重大设计变更 | 说明动机与影响 → 询问用户 → 同步 `01-Architecture.md` |
| L2 | 产品定义、技术栈基线、许可证基线、里程碑验收口径 | **先与用户确认 → 同步真理源 → 再开工** |

发现 L1/L2 项及时提出、不攒到最后、不替用户裁决。
