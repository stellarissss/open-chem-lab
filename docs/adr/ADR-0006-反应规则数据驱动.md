# ADR-0006 · 反应规则数据驱动，不硬编码进 WASM

- **状态**：已接受（2026-11-14）
- **关联**：ADR-0002（分层）、`design/02`、`design/03`、`design/05`、`research/02`

## 背景

2026-11-14 实读 `MaxBittker/sandspiel` 的 `crate/src/species.rs`（`crate/` 目录树经 GitHub API 枚举：`lib.rs / species.rs / utils.rs / tests/web.rs`）：

```rust
#[repr(u8)]
pub enum Species { Empty=0, Wall=1, Sand=2, Water=3, /* …约 20 种，u8 硬编码… */ }

impl Species {
    pub fn update(&self, cell: Cell, api: SandApi) {
        match self {
            Species::Sand  => update_sand(cell, api),
            Species::Water => update_water(cell, api),
            /* 每种物质一个硬编码分支 */
        }
    }
}

// 反应 = 邻域采样 + 硬编码 if/else
pub fn update_lava(cell, api) {
    if api.get(dx,dy).species == Species::Water {
        api.set(0,0, Cell{ species: Species::Stone, .. });  // 岩浆遇水→石头
    }
}
```

**结论**：Sandspiel 的反应逻辑与物质种类**编译期固定**。`Cell` 为 `{ species:u8, ra:u8, rb:u8, clock:u8 }`；`SandApi` 提供 `get/set/get_fluid/set_fluid(Wind)/rand_*`；流体风场已实现压强/密度耦合（可作 NB「压强系统」的物理底座）。

若沿用此结构，**每加一个物质/反应都要改 Rust 并重编译 WASM** —— 与 `CHARTER` D4「上万物质/反应」和「长期可维护/内容由社区生产」根本冲突。GitHub 检索 `reaction SMARTS template extraction` 返回 **0** 结果、`chemical reaction rule engine` 仅 1 个 ★0 仓库，说明这一层没有现成开源方案，是本项目核心自研价值。

## 备选

| 方案 | 判断 |
|---|---|
| A. 沿用 Sandspiel 硬编码 match，物质编译进 WASM | 起步最快，但撑不到上千物质，内容无法社区生产，长期不可维护 |
| B. 全部反应放服务端求解 | 客户端无实时性，断网不可玩，违反 ADR-0003 |
| **C. 数据驱动规则包 + 本地二进制下发** | 内容与引擎解耦，断网可玩，可版本化/回滚/社区生产 |

## 决策

**采用 C**：把「物质定义」与「反应逻辑」从 Rust 代码中抽出，改为运行时加载的数据。

1. **材质表（MaterialTable）**：`enum Species` → 运行时 `Material { id:u16, phase, density, color, thermal, conductivity, reactivity_class, flags }`，从规则包加载；表现材质 ≤ 512 种。
2. **Cell 扩展**：`{ material_id:u16, amount:u16, temp:i16, aux:u16 }`（8 字节，M0 实测 60fps 可行性）。
3. **通用更新循环**：不再 `match` 每种物质；每帧对相邻 cell 对计算 `pair_key = (min(id), max(id), 条件桶)` → 查本地编译规则包（哈希/完美哈希）→ 命中则生成 `CellTransform{from,to,coeff,effects[]}`，未命中只做物理运动。
4. **条件桶**：温度/浓度/pH/压强/催化剂离散化，避免浮点规则爆炸。
5. **规则单一事实源**：`content/rules/*.yaml`（`design/03` schema）→ `rule-compiler` 编译成二进制 → 启动时载入 WASM 线性内存 / IndexedDB 缓存，**断网可玩**；服务端夜间按未覆盖日志重编译下发 Top-N 高频规则。
6. **化学计量守恒**：以 `amount` 按系数消耗/生成，避免「无限产物质」。

## 理由

1. **兑现 D4**：上万化合物资料卡在服务端，只有 Top-N 高频规则编译进客户端 —— 规模与 60fps 不矛盾。
2. **内容即数据**：规则是可 review 的 YAML，支持 diff、回滚、社区 PR、`confidence` 闸门、CI 黄金用例（ADR-0002 正确性）。
3. **可演进 / 可替换**：引擎与规则解耦后，可换求解器、加系统（电流/光照/催化）而不重写引擎。
4. **不重复造轮子**：只改造 Sandspiel 的「物质定义与反应查询」两处，网格、风场、WebGL 渲染、WASM 构建链全部保留。

## 影响

- `design/02` 第二节给出完整改造方案；`design/03` 给出规则 schema 与编译管线；`design/05` 把 `rule-compiler`/`content/` 列为独立包与目录。
- `sim-core` 只认识材质 ID，不认识分子；`rule-engine` 只认识规则与现象 ID，不认识渲染 —— 通过 `ocl.phenomenon.v1` 协议解耦。
- CI：`schema-validate` + `rule-lint` + `golden-cases` + `license-scan`。

## 待 M0 验证

1. 在 fork 里把一条反应改成查表，确认「不重编译即可改反应」或评估重编译可接受度。
2. 8 字节 Cell + 512² 网格在中端设备能否稳定 60fps（不达标则 256² / 脏矩形更新）。
3. 完美哈希/规则包体积（目标 Top 2000 条 < 2 MB）。

## 反面约束

禁止把反应重新硬编码回 `match` 分支；禁止在客户端做未授权的反应预测（见 ADR-0002）。
