# 12 · 阶段二开发流程（可行性验证 / M0）

> **状态**：生效（2026-11-15 制定）· 上位依据：`CHARTER.md` 第 2 条（开发规范）、第 6 条（阶段划分）、[决策台账](11-问题与决策台账.md)、[`docs/10` 第六节](10-完整规划与风险登记册.md) M0 十项验证清单。
> **适用范围**：阶段二（M0 基座验证）。阶段三（M1–M4）另立流程，不套用本文件。
> **一句话**：阶段二**不写产品代码，只消解不确定性**；每个结论必须由「一级来源 + 可重跑最小测试」双支撑，凡效果不好的必须换用/提升，凡触及固定裁决的必须交用户裁决。

## 一、阶段二的目标与边界

| 项 | 定义 |
|---|---|
| 目标 | 把阶段一「纸面锁定」的技术选型逐项放到真实环境里跑一遍，消解不确定性，输出**可复现的实测证据** |
| 不做 | 不实现 M1 垂直切片、不堆反应数、不提前做教学层、不引入工坊 / MOD / 虚构物质 |
| 成功标准 | M0 十项验证全部「通过」或「产出替代方案 ADR」；无时间预算，以质量闸门为准（台账 1.1） |
| 红线 | 数值零错、许可证兼容、Win + Linux 双平台、不重复造轮子；任一不达标即触发偏差流程 |

> 阶段一已把所有「做什么/为什么」写死；阶段二回答的是「**这些选择在真实世界是否成立**」。因此本阶段最有价值的产出不是「一切通过」，而是**抓出规划与实况的偏差**。

## 二、流程闭环（九步，不可跳步）

```
S1 通读     通读 CHARTER / 台账 / 全部设计与 ADR，提取待验证项与固定裁决
  ↓
S2 核实     一级来源核实：官方 API、LICENSE 原文、CTAN/PyPI/npm 元数据、官方测试用例
  ↓          （搜索引擎仅作线索；不得把结果页当事实）
S3 实测     搭建隔离环境，跑最小测试；原始数据 + 可重跑脚本归档入库
  ↓
S4 判定     对照质量闸门逐项判定：通过 / 不通过 / 受限（环境无法覆盖）
  ↓
S5 登记     偏差分级 L0 / L1 / L2，登记到 M0 核验报告
  ↓
S6 决策     L0 主管直修；L1 提 ADR；L2 交用户裁决（询问工具，逐项固定）
  ↓
S7 修订     按裁决修订 ADR / 设计文档 / 台账 / 索引 / CHANGELOG / CI
  ↓
S8 复验     重跑受影响测试 + CI 门禁 + 内部链接 + 旧口径回归扫描
  ↓
S9 交付     归档实测数据，提交并推送 main（ghfast.top 镜像），呈现交付物
```

**核心纪律**：S2 的关键事实必须打开原文核实，S3 的最小测试必须可重跑并留档，S6 的矛盾点必须逐项固定、不得由主管替用户裁决。

## 三、质量闸门（S4 判定标准）

| 闸门 | 判定标准 |
|---|---|
| **数值零错** | 与独立解析解 / 权威常数比对，误差在预设容差内；`sane=True`、无负浓度 |
| **可复现** | 版本号、依赖清单、命令、输入全部留档；换机器可重跑 |
| **依赖可控** | 直接依赖数、传递依赖、镜像体积与安装耗时可接受；不得拖入与用途无关的栈 |
| **许可证兼容** | 逐项核实 LICENSE 原文；AGPL / GPLv2-only 隔离；LGPL 义务可落地 |
| **双平台** | Linux 实测 + Windows 静态规范核查；无法覆盖的显式标「受限」并给出补验方案 |
| **不重复造轮子** | 存在成熟开源实现且效果达标即复用；自研仅限 CHARTER 允许的四类 |

## 四、偏差分级与处置（S5 / S6）

| 级别 | 含义 | 处置 | 是否需用户裁决 |
|---|---|---|---|
| **L0** | 工程实现错误（命令写错、参数名错、单位错、文档描述与实物不符但未改变选型） | 主管直修 + 在报告与 CHANGELOG 登记 | 否 |
| **L1** | 技术选型调整（换组件 / 换工具链 / 换实现路径），不触碰 CHARTER 固定裁决 | 提 ADR，说明动机与影响，同步设计文档 | 建议裁决 |
| **L2** | 触及 CHARTER 第 0/2/3 条、台账固定裁决、许可证基线或产品定义 | **必须交用户裁决**，再按 CHARTER 第 7 条走 ADR + 台账登记 | **是** |

> S6 裁决结果写入台账，作为后续所有文档的依据；**修订不得绕过台账**（台账为唯一事实源）。

## 五、调研方法（本阶段实测后的强制调整）

阶段二首次调研发现：长英文技术查询在聚合搜索下**结果严重污染**（返回无关商品、语音小说、成人内容；中文查询被切词误导）。因此本阶段起固定以下方法：

1. **官方 API / 原文为主**：GitHub contents API 读 LICENSE 与官方测试用例、PyPI JSON API 读版本与依赖、npm view 读许可证、CTAN 读宏包元数据、Crossref 读 DOI。
2. **搜索引擎仅作线索**：只用于发现候选与入口，采信前必须打开原文二次核实；遇验证码立即停止该引擎（不规避）。
3. **官方测试用例优先于文档**：文档常改版 404，仓库内 `tests/` 与 `examples/` 是 API 用法的一级来源。
4. **star 数统一标快照日期**（本阶段快照日 2026-11-15），不把动态值当固定事实。

## 六、实测记录规范（S3 / S9）

- 每个最小测试产出：可重跑脚本 + 结构化 JSON 结果（含期望值、实测值、绝对误差、容差、耗时、来源）。
- 原始数据统一归档至 `docs/research/data/m0/`，并在 `INDEX.json` 登记；**测试脚本不进产品构建**。
- 期望值必须来自**独立解析解或权威常数**，不得由被测库自证（避免循环论证）。
- 失败项不得静默丢弃：记录失败原因、根因、修正动作与复验结果（本阶段即经历 3 轮 API 对齐才跑通四体系）。
- 归档脚本与结果必须成对且可重跑：S8 须做一致性审计，确认每组 JSON 确由同名脚本产出。本阶段据此处置了 3 处「脚本与结果版本错配」（详见 `research/04` §4.6），其中一条虚假 FAIL 源自调试代码异常落入 `except` 分支。

## 七、本阶段已固定的工程约定（由实测得出）

| 约定 | 依据 |
|---|---|
| 依赖必须装进隔离环境（venv / 容器 + lockfile），禁止全局 pip | 全局安装 `pyequion2` 把 `tinycss2` 降到 1.4.0，破坏预装 weasyprint |
| 容器健康检查必须等依赖装完，不能只看进程存活 | 首轮 Compose 显示 Healthy 但 `chempy` 尚未装完，`import` 失败 |
| 刚性 ODE 由求解器数值特性自动判定，不硬编码时间阈值 | 实测刚性体系 RK45 42500 次求值/259ms，LSODA 262 次/1.48ms（约 175 倍） |
| 求解快照与渲染解耦，帧预算按 16.7ms 独立核算 | 500 粒子软件渲染 p95 1.2ms，稳态求解约 11.5ms，均在预算内 |
| 受限项必须显式标注，不得写成「通过」 | Windows 侧、WASM 工具链、WebGL 无头渲染在本沙箱无法覆盖 |
